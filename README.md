# 火影忍者手游替身计时器（纯视觉）

v0.1.6 修复新版训练场「复位、音乐」工具栏导致的画面未识别，并避免旧 ZIP 场景资源覆盖新版 EXE。保留完整 OCR/VC 依赖、启动日志与神驹斑扫光修复，详见 [修复说明](docs/release-v0.1.6.md)。

本项目以 MIT License 开源。Windows x64 发布版见 [GitHub Releases](https://github.com/fangxiaobaiqaq1/naruto-substitute-timer/releases/latest)。下载单独的 `timer-app.exe` 放在可写目录运行，或解压完整 ZIP 后运行「启动计时器.bat」。先启动 MuMu 和游戏，程序自动查找安装目录（默认实例 0）。首次启动在程序目录创建 `config.json`；请在设置中填写自己的账号名或手动选边。程序只读取模拟器画面，不读取游戏内存。

v0.1.3 将本地 PP-OCRv4 中文识别模型、CPU 推理运行库、完整解包忍者资料库和替身表一并内置进 EXE；场景模板与掩码也继续内置。普通忍者姓名通过 OCR 与资料库核对，无需逐个收集名字截图，也无需安装 Python 或系统中文 OCR 语言包。资料库有 2490 条目录记录，含变体和内部项，不等于 2490 名可玩忍者或识别准确率保证。点击「诊断」可查看版本、OCR 后端、库数量和失败原因，排查是否启动了旧 EXE。变更与验证范围见 [v0.1.3 说明](docs/release-v0.1.3.md)。

运行环境为 Windows 10/11 x64。发布版已内置 ONNX 所需的四个 Microsoft Visual C++ v14 x64 DLL，无需另外安装运行库；按整套资源的哈希释放到用户缓存，限定目录加载并核对实际模块路径。

> 当前改造与运行入口见 [低延迟版本与诊断](docs/低延迟版本与诊断.md)。下文保留了早期实现记录；界面、采样周期、冷却时间和布局描述应以当前配置及源码为准。

通过截取 MuMu 模拟器窗口画面，纯视觉识别替身豆状态并计时。**不读取任何内存**。

## 架构总览

分层架构，严格解耦（依赖方向自下而上，禁止反向依赖）：

```
┌─────────────────────────────────────────────────┐
│ cmd/timer         CLI（win/beads/capture/list）  │
│ cmd/timer-gui     校准工具（实时截图+豆位框）      │
│ cmd/timer-app     正式前端（豆状态面板）          │
├─────────────────────────────────────────────────┤
│ internal/frame    数据帧类型 + Snapshot 组装层    │
│ internal/gui      校准工具 UI（Win32）            │
│ internal/app      前端 UI（Win32）               │
├─────────────────────────────────────────────────┤
│ internal/detect   豆位检测算法（纯函数，无 UI）    │
│ internal/win      窗口查找 + 截屏（纯 Win32）     │
├─────────────────────────────────────────────────┤
│ internal/draw     标注绘制（菱形框/编号/填充）     │
│ internal/win32    最小 Win32 API 绑定（共用）     │
└─────────────────────────────────────────────────┘
```

- `internal/win32`：纯 API 绑定，两个 UI 共用，不包含任何业务逻辑
- `internal/draw`：标注绘制层。**标注（红框、L1~R4 编号）只画在截图副本上，绝不回写原始截图**——识别永远基于原始图像，标注不影响识别
- `internal/frame`：唯一的粘合点之一，把 `win`（截屏）+ `detect`（检测）组装成 UI 可直接消费的 `Frame`，两个 UI 共用，避免复制组装代码
- `internal/gui` 与 `internal/app` 约定：**不 import `internal/win` 与 `internal/detect`**，只通过 `frame.Provider` 回调拿数据

## 界面布局（决斗场）

画面顶部 UI 层级（从上到下）：

1. **角色名字**（y≈66~84 客户区，白字 + 橙色装饰）
2. **血条**（y≈88~94 客户区）—— 连续的橙/红色横条，左右长度不同 = 血量不同。**检测豆子时必须排除血条**，血条颜色会落入赤金区间造成误判
3. **替身豆**（y≈100~118 客户区 = 内容区 y≈80~98）—— 4 颗豆一行，位于血条正下方

## 豆子充能规则（关键）

- 左右各 4 颗豆，按 **1→2→3→4 顺序递增充能**
- 充能中/可用的豆子显示为**亮蓝色**，未充能的显示为**暗青色**（菱形主体）
- **绝不允许出现"豆2 亮而豆1 暗"的状态**——前面亮了后面才可能亮（连续前缀）
- 检测结果若违反递增约束，视为采样错误（豆位偏移/界面不对），需修正豆位或判定非对局画面

## 豆子原生形状（关键，抗环境特效）

- 替身豆是**竖向菱形**（非圆形）：顶部尖点 → 中部最宽 → 底部尖点
- 像素级实测（客户区 1092×654）：亮蓝主体 **11px 宽 × 16px 高**；暗色描边外约 1px 发光
- 用户参考图（豆子特写 23×26）确认：菱形中部有一条**横向暗青装饰带**，是豆子固有纹理，不是两颗粒子
- 检测投票区域用 **13×18 菱形**（比主体宽高各 +2px 容错描边/发光），贴合原生轮廓：
  - 菱形方程 `|dx|/(w/2) + |dy|/(h/2) ≤ 1`（`internal/detect/beads.go` 的 `InBeadDiamond`，整数运算）
  - 避免方形/圆形邻域把豆间隙、血条或环境特效计入投票
- 标注图（`annotated.png`）用红色菱形框贴合豆子轮廓，供人工审核

## 镜像规则（关键）

- **右侧豆子的编号与左侧镜像**：左侧豆1 在最左（从左到右充能），右侧豆1 在最右（从右到左充能）
- 即左侧从左到右显示为 豆1..豆4；右侧从左到右显示为 豆4..豆1
- 因此右侧检测结果若从左到右排列，状态序列与左侧**相反**（如左侧"亮亮暗暗"，右侧为"暗暗亮亮"）
- 代码中右侧 Bead 数组按"右→左"（豆1 在右）排列，保证递增约束对两侧一致生效

## 豆子标定（1920×1080 逻辑坐标）【已人工确认 ✓】

| 豆 | 左侧（左→右） | 右侧（右→左，镜像） |
|----|------|------|
| 1  | (195, 155) | (1674, 155) |
| 2  | (225, 155) | (1644, 155) |
| 3  | (255, 155) | (1614, 155) |
| 4  | (285, 155) | (1584, 155) |

**标定规则（关键）：左右对称 + 30px 均匀间隔**

1. 左侧豆位经用户实测红圈 + 像素级列统计确认完全正确：195 / 225 / 255 / 285（**30px 均匀间隔**）
2. 右侧与左侧镜像对称，必须保持同样 **30px 均匀间隔**：1674 / 1644 / 1614 / 1584
3. 校验方法：任意相邻豆距 ≠ 30px 即标定错误（曾因 R3=1612、R4=1582 各自偏左 2px 被用户指出）
4. 1092×654 客户区实测豆心：左 x=110,127,145,162；右 x=952,935,917,900（右→左）；y=108

注意：右侧 x≈960~985 是替身冷却显示区（暗青+蓝混合 UI），**不是豆子**，勿误检。

豆子参考图（用户提供，23×26 特写）：主体深蓝青色 RGB(16,112,128)——该色介于暗青与亮蓝之间，疑为充能中动画的中间帧或界面光照差异；实测决斗场画面仅出现亮蓝 (≈174,244,250) 与暗青 (≈24,51,96) 两态，分类范围保持不变，若后续画面出现第三色需复查。

**环境特效干扰（实测）**：决斗场右侧常有蓝色光效斑块（深蓝青 ≈RGB(18,117,129)）落在豆间隙甚至豆子边缘，会与"充能中"动画混淆。实测两帧对比确认豆子的**物理中心是暗青核心**（左半暗青+右半深蓝青渐变中的暗青部分），特效斑块位置逐帧漂移而暗青核心稳定；豆位按暗青核心标定后两帧采样一致。

## 检测算法

1. **场景门闩**（`internal/scene`）：先在 HUD 路标上做灰度 NCC。`scene.manifest` 为空或默认相对路径 `assets/templates/manifest.json` 时，始终使用 EXE 内置的清单、模板和遮罩，升级 EXE 不会被旧 ZIP 遗留资源覆盖。需要自定义时，复制清单为其他路径（例如 `assets/templates/custom-manifest.json`），再设置 `scene.manifest`；自定义清单中的图片路径相对于清单目录读取。`config.scene.fightScenes` 列出哪些算对局。匹上对局才采豆；看不清 → Hold（钟不动）；路标明显消失 → 离场。自定义清单缺失或没有可用模板时回退旧的颜色密度 `ClassifyScreen`。
2. **豆心采样投票**：对每颗豆的标定位置取菱形邻域逐像素分类，按 亮 / 暗 / 未知 多数胜出
3. **颜色分类**（`internal/detect`，RGB 阈值）：
   - 亮蓝（充能完毕/可用）：R 0~229，G 120~259，B 170~259
   - 暗青（未充能/冷却中）：R 13~64，G 3~59，B 1~107
   - 赤金（血条）：用于排除血条区域，不计入豆子
   - 深蓝青 ≈RGB(18,117,129) 是环境特效/充能动画中间色，**不计为亮**
4. **递增修正**（`ApplyIncrementRule`）：豆 1→2→3→4 连续前缀充能，任何"前暗后亮"视为采样错误，按前缀规则纠正为合法状态
5. **计时**（`SideClock`）：对局中连续确认后，掉 1 颗可用豆开 13.5s；掉 4 颗当大招不计；掉 2/3 或闪一下忽略。起点是第一次看到掉豆的抓帧时刻。连续离场帧后两侧钟清零。

## 坐标映射

- 逻辑分辨率：1920×1080（游戏 UI 基准）
- 客户区 → 内容区：MuMu 窗口顶部有约 20px 边框，内容区 = 客户区裁剪 (0,20)，尺寸 1092×614（随窗口缩放）
- 内容区 → 逻辑：`逻辑x = 内容x * 1920/1092`，`逻辑y = 内容y * 1080/614`
- 支持窗口任意缩放：客户区 16:9 铺满或等比黑边模式（ModeAuto/ModeStretch/ModeLetterbox）

## 窗口与截屏（internal/win）

- 窗口查找：`EnumWindows` 按进程名匹配 MuMu（本机 `MuMuNxDevice.exe`，窗口标题"MuMu安卓设备"；工具窗口是黑屏，不要选）
- 截屏：**`PrintWindow + PW_RENDERFULLCONTENT`**（BitBlt 抓不到 MuMu 的 GPU 渲染内容），失败回退 BitBlt
- 每次采集都重新查找窗口并截取当前客户区 → 天然跟随**窗口更换**与**尺寸变化**

## UI 架构（关键设计）

两个 UI 共用同一套事件驱动采集模型，**PrintWindow 卡住也不会卡界面**：

```
UI 主线程 (消息循环, LockOSThread)    worker goroutine
──────────────────────────────      ────────────────
WM_TIMER (2s) ──trigger──▶          provider() → pending
按钮点击 ──────trigger──▶            （PrintWindow 卡住只卡这里）
   │
   └─ consumePending() ─ 取最新帧 → 更新豆灯 → InvalidateRect
```

- **事件驱动**：worker 收到触发才调 provider（截屏），完成后写入 `pending`；主线程只消费，两者用 mutex 保护
- **非阻塞触发**：worker 忙时（上一帧未完成）`select default` 跳过本次触发并置粘滞标志，采完自动补一轮（不丢请求）
- **线程绑定（关键修复）**：`runtime.LockOSThread()` 把消息循环锁在创建窗口的 OS 线程上。Win32 窗口/消息队列与创建它的线程绑定，goroutine 被 Go 调度器迁移到别的线程后 `GetMessageW` 永远收不到消息 → 窗口假死、被系统判定 AppHang 自动关闭。曾因缺少这行出现"启动慢/随机自己关闭"，锁线程后根治
- **采集慢自动降频**：上次采集 >2s（MuMu 忙）时跳过本轮触发，连续跳过 2 轮后强制采集一次，MuMu 恢复后自动自愈
- **双缓冲**：paint 全部画到内存 DC，一次 BitBlt 上屏（无闪烁）；背景渐变复用 `panelBuf`，不逐帧分配 2MB
- **性能实测**：采集 9~30ms（MuMu 空闲时），WATCHDOG 0 次卡死，内存 ~74MB 稳定

### 校准工具 timer-gui

实时刷新（500ms）显示 MuMu 截图 + 红色菱形豆位框 + 编号，用于验证相对坐标算法。**开发调试用**，持续截屏开销大。

### 正式前端 timer-app

界面框架参考 K0NGCH4NG/Naruto_Mobile_Game_Tool：左右两侧替身豆列 + 中间状态区 + 底部按钮行。**无背景图、无原生控件，全部 GDI 自绘**：

```
┌─────────────────────────────────────────┐
│ 替身计时器               纯视觉 · 不读内存 │
│   L1 ◆      [2 / 2]        ◆ R1          │
│   L2 ◆      可用替身        ◆ R2          │
│   L3 ◆       对局中         ◆ R3          │
│   L4 ◆                     ◆ R4          │
│ [查看豆位框] [刷新] [置顶] [退出]          │
│  MuMu安卓设备 · 采集 12ms                 │
└─────────────────────────────────────────┘
```

- 窗口固定 **560×420**（WS_OVERLAPPED 去掉 WS_THICKFRAME/WS_MAXIMIZEBOX，不可缩放变形）
- **左右豆列**：L1-L4 / R1-R4 纵向排列，镜像游戏内布局（左列在左下、右列在右下）；豆子三层菱形（外发光 + 主菱形 + 内核 + 描边），亮 = 亮蓝、暗 = 深蓝、未知 = 灰
- **中间状态区**：可用替身数大字 `2 / 2` + 画面状态（对局中 = 橙金 / 等待画面 = 灰 / 未找到窗口 = 红）
- **自绘按钮**：查看豆位框（开启时橙色描边）、刷新、置顶（开启时橙色描边）、退出（红色系）；hover 高亮 + 手型光标，鼠标命中检测在 WM_LBUTTONDOWN/WM_SETCURSOR 中处理
- **默认不截屏不卡**：后台 2s 事件驱动采集一次（实测 9~30ms），只更新豆灯
- **"查看豆位框"默认关闭**：点击后才截取**一张静态截图**（红框 + L1~R4 编号，fit 缩放显示全窗口 + 顶部"返回"按钮），勾选期间**停止自动采集**，点"刷新"才重拍
- **置顶**：对局时可把前端悬浮在游戏窗口上方
- 状态栏显示窗口信息 + 最近一次采集耗时

## 构建与运行

Windows x64 需要 Go 和可用的 C/C++ 编译工具链（Fyne 与本地 ONNX 绑定使用 cgo）。**运行 `build.bat`**，生成 CLI、校准工具、正式前端、调试前端和诊断工具五个 EXE 到 `bin\`。脚本会准备 Fyne 绘制诊断补丁；直接执行普通 `go build ./cmd/timer-app` 不等价，不能据此报告到真实绘制提交的端到端延迟。

发布构建先在命令提示符中执行 `set TIMER_VERSION=v0.1.6`，再运行 `build.bat`；未设置时诊断页显示 `development`。本地 OCR 所需模型和 DLL 已在源码中，无需额外下载语言模型。第三方运行依赖的许可与再分发要求见 `THIRD_PARTY_NOTICES.md`。

```bash
# CLI（调试）
bin/timer.exe win              # 查找 MuMu 窗口并显示客户区
bin/timer.exe beads            # 按当前窗口客户区计算替身豆实际坐标
bin/timer.exe capture          # 截取客户区保存 PNG + 豆位采样 RGB + 生成 annotated.png 标注图
	bin/timer.exe list             # 列出所有顶层窗口（调试用）
	bin/timer.exe scene dump.png   # 打印各模板分数和场景结论
	bin/timer.exe crop -image dump.png -roi 0.42,0.02,0.16,0.10 -out assets/templates/foo.png

	# 校准工具（实时截图 + 豆位框）
	bin/timer-gui.exe

# 正式前端（-H windowsgui = 无黑色控制台窗口）
bin/timer-app.exe
```

> 说明：`timer-gui` 与 `timer-app` 必须用 `-H windowsgui` 构建，否则启动时带黑色 cmd 窗口。
> 调试排障：`set NARUTO_DEBUG=1` 后运行 `bin/timer-app.exe 2>debug\app.log` 可输出运行日志
> （窗口查找、采集心跳、panic 堆栈、主线程卡死 watchdog）。

## 计时怎么用

完整说明见 [docs/使用说明.md](docs/使用说明.md)。

1. 开 `timer-app`。自动模式在 VS / 死亡换人时识别底栏账号，在对局中也会识别顶部账号名。
2. **我方名字自己填**：`config.json` 的 `ui.playerNames`。VS 名字模板放在 `assets/identity/`，对局顶部的名字模板放在 `assets/identity/fight/`；详见该目录的 README。
3. **对面名字**也会认：把对面账号图放进同一目录；对不上会裁到 `assets/identity/seen/`。
4. 掉 1 豆开 **15 秒**（用那一帧时间戳算剩余）；掉 4 豆当大招不计。死亡换人 / VS **不清钟**。只有大厅 / 结算才清。
5. 认错边就点「换边」，或在设置的**我方所在边**选择「自动认边 / 左边 / 右边」，点选立即生效，不必再点保存。浮窗始终显示对面（我方在左 → 对面在右）。没有可信认边结果时显示「对面·待认边」，不猜对面的计时。
6. 「记住认边方式」只保存所选模式；自动识别结果不会被写成手动锁边。取消勾选后，本次手动选择仍生效，下次启动回到自动。

解包抽到的技能/替身表、HUD 截图 ROI、以及为什么图集解不开：见 [docs/解包与视觉数据.md](docs/解包与视觉数据.md)。APK 全量树在 `unpack/`（[unpack/reports/00_INDEX.md](unpack/reports/00_INDEX.md)）。计时器运行时仍不读内存。

## 后台中文文字识别与诊断

在设置中可即时开启/关闭「后台识别名字（内置本地 OCR）」。Windows x64 发布版使用内置 PP-OCRv4，采豆不等待 OCR；至少两个视图及两次不同采集时间的结果一致，且当前字形仍匹配才接受。库内姓名支持中点，例如「萨克·镫」。模型读错或缺字时仍可能显示“待确认”或“忍者未确认”，不自动替换错字、猜测忍者版本。手动选择和已有特殊豆型模板继续优先。

首次使用 OCR 时，内置运行库解到当前用户缓存目录的 `naruto-timer/ocr/<整套文件SHA256>/`，同版本复用、校验并自动修复损坏文件；图片通过本机管道处理，不联网识别。运行库无法加载或识别超时时可在「诊断」查看状态，其他检测路径继续运行。「打开 OCR 启动日志」可查看 `%LOCALAPPDATA%/naruto-timer/logs/` 中的完整错误码、原因、程序版本和实际模块路径。仅保留最后一次失败和最新成功状态两个 JSON，不包含游戏图像。模型、运行库和第三方许可说明见 [本地 OCR 资源](internal/ocr/neuraldata/README.md)。

采集日志和原帧录制可从「诊断」开启；原帧只在有效对局中保存，受队列与容量上限约束。报告分别列出采集、分析、确认、UI 投递和绘制阶段；无有效帧、未绘制结果、单个函数耗时不会作为完整端到端延迟样本。详见 [前端诊断与原帧录制](docs/前端诊断与原帧录制.md)。

离线诊断：`bin/timer-lab.exe ocr -image <游戏整图.png>`。只有显式指定 `-out` 才保存包含姓名的原始文字报告。实时 `observe` 将无有效帧报告为失败/无延迟值，不能把重试速度当成帧率。
