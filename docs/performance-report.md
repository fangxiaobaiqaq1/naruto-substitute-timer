# 电脑端性能报告

用于排查**卡顿、CPU/内存/显存占用、疑似内存增长、线程/句柄增长、采集或 UI 调度变慢**。它与原有“采集与延迟诊断 / 原帧录制”独立，不会自动录制游戏图像、启动回放或上传数据。

## 使用方法

1. 主窗口点击独立的 **「性能报告」** 按钮。设置页、原诊断窗口也有入口；迷你模式可从设置进入。
2. 点击 **「开始性能监测」**。默认每秒采样一次；可选择附加开始/结束的 Go 堆和协程快照。
3. 继续正常使用，复现卡顿时点 **「标记卡顿」**。建议至少记录几十秒至数分钟，包含正常阶段与异常阶段，不要用刚启动的两三个样本判断泄漏。
4. 点击 **「停止并导出 ZIP」**。也可在监测中导出当前一致快照，不读取尚未提交的文件尾部。
5. 解压 ZIP，打开 **`report.html`**。无需网络、服务或浏览器扩展；保留整个目录，可继续读取原始 JSON/CSV。

关闭性能窗口不会停止监测，主窗口按钮仍显示“进行中”；这样也能减少查看实时面板本身带来的绘制开销。真正退出程序会停止监测并保留原始数据。**未开启前没有历史记录，不能回溯此前卡顿。**

性能监测与全量诊断可以同时开启；报告会记录此状态，图像编码/写盘等额外开销也会被测到。排查纯占用时优先只开性能监测；排查识别误判、豆位或截图问题再开全量诊断。

## 能看到什么

| 范围 | 数据 |
|---|---|
| 环境 | 应用/Go/系统版本、构建标识（可用时）、CPU型号及逻辑核数、进程和原生架构、RAM、GPU型号/驱动及能力缺失原因 |
| CPU | 系统、主进程、已观测进程树的CPU时间口径百分比；CPU核等效；累计CPU时间、实际计数器时间窗和时效 |
| RAM | 工作集/RSS、Windows私有提交、虚拟地址空间、系统可用物理内存/提交量与上限；生命周期峰值与本会话峰值分别解释 |
| Go运行时 | 堆分配/在用/保留/空闲/归还、栈、对象数、分配速率、GC次数/频率/STW暂停/GC CPU、实际GOGC/GOMEMLIMIT/GOMAXPROCS、协程数 |
| 进程 | 主进程与已观测后代的PID/父PID、创建身份、线程、句柄/FD、GDI/USER对象（Windows）、I/O与页错误 |
| GPU | 系统/主进程/进程树最忙引擎、每进程引擎观测、专用/共享GPU内存；依赖WDDM/PDH及驱动支持 |
| 应用链路 | 采样/分析次数率、重复/hold/错误/超预算计数、尺寸、采集后端、采集/分析/交付帧龄、窗口P95、UI队列等待 |
| 诊断自身 | 计数器采样/统计耗时、采样缺口、卡顿标记、不可用/部分聚合/限额状态、导出时的标记 |

实时窗口提供当前读数和明细。离线 HTML 提供时间曲线、首末/峰值/均值/P50/P95/P99、每分钟趋势、进程汇总、采样缺口和标记。JSONL/CSV 保留完整已提交采样前缀，图表压缩显示不会删除原始数据。

## ZIP 文件

- `report.html`：离线图表与可读报告。
- `report.md`：文本摘要和指标表。
- `metadata.json`：系统、构建、安全配置和口径说明。
- `summary.json`：统计、趋势、进程汇总、可用性和事件。
- `samples.jsonl`、`samples.csv`：完整采样时序。
- 可选 `heap-start.pprof` / `heap-end.pprof`：采样 Go 堆，不是完整内存转储，不含 ORT 原生堆。
- 可选 `goroutines-start.txt` / `goroutines-end.txt`：调用栈，便于查阻塞/协程增长。

快照中的绝对文件路径简化为文件名，保留函数/行号；原始 profile 通过内存管道脱敏，不先写到磁盘。快照不强制 GC；堆差分必须结合最近 GC 和缓存预热看，不能机械等同于存活泄漏。

例如开发者可使用：

```sh
go tool pprof -base heap-start.pprof heap-end.pprof
```

## 必须区分的口径

- **CPU 核等效不是整机百分比。** 一个逻辑处理器持续忙碌为1核等效；按系统逻辑核数归一后才是CPU%。这不是频率加权的CPU utility。
- **进程树不是整台电脑。** 独立模拟器和预先运行的ADB服务不属于本进程树；采样之间创建并退出的短命子进程可能漏计。PID复用不会跨身份计算增量。
- **工作集合计可能重复共享页。** Windows私有提交不是Linux私有驻留，也不是Go堆；原生SDK、ORT、驱动内存需要看进程/系统指标。
- **系统GPU与我们的GPU不同。** 显示最忙引擎，不把不同engine百分比直接相加。OCR的“请求GPU”开关不代表实际后端已经启用。
- **进程I/O不是纯物理磁盘吞吐。** 它可以包含管道、设备和缓存读取；页错误也包含软错误。
- **采样/分析次数率不是游戏FPS。** UI排队时间不是GPU呈现时间，更不是显示器发光延迟。
- **缺失不是0。** 初始速率需要建立基线；驱动不支持、权限不足、计数器重置、超限等都有说明。部分聚合不能当完整进程树结果。
- **增长不是泄漏结论。** 报告给增长线索，不自动判定泄漏。更长观测、同场景对照、Go堆差分和原生内存数据需要共同判断。

## 开销和边界

- 默认关闭，不随程序重启自动恢复；未开启时捕获路径仅检查是否存在监测会话。
- 低频后台采样，不在捕获线程或UI线程执行系统扫描、profile生成和ZIP导出；UI通知合并，不积压每帧刷新任务。
- 最多21600个样本（1Hz约6小时）或64MiB时间线，先到即停止并记录原因。采样/系统调度延迟可能延长实际时长。
- 已观测进程树最多64个，GPU引擎行最多256个；达到扫描/容量预算时明确标注不完整，而不是伪造完整统计。
- 可选堆快照每份最多16MiB、协程文本每份最多4MiB；图表/汇总/导出临时文件和ZIP另占空间。
- 同一会话重复导出替换固定 `performance-report.zip`，失败保留旧导出；不同会话使用独立目录。历史报告不自动删除，不再需要时可手动清理。
- 数据保存在配置的debug目录下的 `performance/perf-时间-随机标识/`。不附加原config、截图、游戏账号、命令行、环境变量或其他程序的名称，不自动上传。
- GPU提供者可能失效或不返回；GPU工作应与CPU/RAM采样隔离，缺测明确显示。Windows真实驱动、权限和原生渲染仍需真机验收，交叉编译不代替运行验证。
- Linux用于开发验证CPU/内存等本地指标；无通用可靠GPU接口时明确unsupported。其他平台不以零值假装已采到原生指标。

## 验证入口

```sh
# Go 1.26.10；已有依赖缓存时可设置 GOPROXY=off
# 核心、采集器、报告、隐私和并发回归
go test -race ./internal/diagnostics
# 前端独立开关、按钮、刷新合并、退出/导出生命周期
go test -race -tags ci ./internal/ui -run 'Performance|Diagnostics|OverlayFit'
# 实际采集本机资源并保留一个可在浏览器检查的报告
NARUTO_PERFORMANCE_SMOKE_DIR=/path/to/local/output \
  go test ./internal/diagnostics -run '^TestPerformanceLiveExport$' -count=1 -v
```

实机验收建议固定模拟器分辨率和场景，分别记录正常对局、持续未知、隐藏/最小化、OCR开/关后、全量诊断开/停后。比较主进程与子进程、CPU和GPU以及帧时间，而不是只看主EXE的某一个内存数字。
