# v0.25 · 速度与内存（测试版）

> 基于 `v0.24beta`（`3256514`）。只做性能和内存：识别结果与 v0.24beta **逐字节相同**（安卓空闲时的分析频率除外，见下）。细节：[Windows](性能优化-windows.md)、[安卓原生核心](性能优化-android-native.md)、[安卓应用](性能优化-android-app.md)。

## 结果

数字来自本机（Xeon E5-2680 v2，只有 SSE2，没有 AVX2）和安卓模拟器，机器同时有别的负载，看相对变化。

### Windows（Go 识别引擎 + 程序）

| 项目 | 之前 | 之后 |
|---|---|---|
| 每帧识别耗时（21 种画面几何平均） | 38.3 ms | 7.35 ms（−81%） |
| 1080p 对局一帧 | 25.1 ms | 5.2 ms |
| 2880×1800 一帧 | 63 ms | 10.7 ms |
| 2560×1600 区域校准（两侧尺度不同） | 319 ms | 37.5 ms |
| 1080p 运行内存（常驻 / 峰值） | 47.7 / 107 MiB | 25.1 / 47 MiB |
| 2880×1800 运行内存（常驻 / 峰值） | 101 / 204 MiB | 53 / 90 MiB |
| timer-app.exe | 81.0 MB | 60.8 MB |

主要做法：模板匹配点积用 SSE2/AVX2（运行时按 CPU 选择，整数结果完全相同）；头像/名字模板按尺寸缓存（校准后不再每帧重建）；MuMu 截图直接写进帧缓冲，翻转+透明度+指纹一遍完成，帧缓冲 3→2；PrintWindow 复用位图（顺带修了一个可能每帧泄漏位图的问题）；去掉不用的数据和每帧格式化；GOGC=50；OCR 助手启动不再对 17 MB DLL 做哈希；`build.bat` 加 `-trimpath -s -w`。

### 安卓原生核心（C++）

| 项目 | 之前 | 之后 |
|---|---|---|
| 17 张真实画面，每帧平均 | 48–63 ms | 11–16 ms |
| 2560×1600 区域校准，每帧平均 | 302 ms | 52 ms |
| 资源注册后内存 | 10.0 MiB | 3.6 MiB |
| 识别引擎建好后内存 | 14.7 MiB | 4.3 MiB |
| 运行后内存（1080p / 2880×1800） | 29.9 / 42.6 MiB | 13.3 / 16.9 MiB |
| 改校准后重建 | ~6 ms | 0.4–0.7 ms |

点积 NEON / DotProd（arm64）与 SSE2/AVX2（x86_64）按 CPU 选择；资源只存灰度和透明位不存 RGBA；同样的按尺寸缓存；并行改进（最多仍 3 个辅助线程）。

### 安卓应用（Kotlin）

- **分析节奏**：按文档实现 —— 对局中每 16 ms、其它画面每 400 ms 分析一次（和 Windows 一样）。之前大厅/选人画面也按屏幕刷新率（60–120 次/秒）分析。进对局最多晚约 0.4 秒被认出，之后切回 16 ms。**这是唯一会改变「分析哪些帧」的改动**，对局中不变。
- 启动加载资源 490 → 308 ms；启动后内存（总 / Java / 原生）55.3 / 25.1 / 19.6 → 36.5 / 7.6 / 18.3 MB（不含原生核心的节省）；无障碍截屏兜底的转换 270–610 → 20–26 ms；录屏取帧不再刷警告；悬浮卡片在对局外不再每 33 ms 轮询。

## 用户视频反馈修复

- **手机识别不了左边的六尾（漩涡鸣人[暴怒·第六尾]）**（视频 `火影忍者(13).mp4`，1920×1080，25.7 秒）：名字模板只按一个尺寸比对，六尾的模板比画面大约小 1%，分数在 0.80 门槛上下晃，很多采集尺寸下名字掉了 → 不知道是鸣人 → 红豆读成「看不清」→ 替身漏计。现在名字精匹配同时试 ±1%、±2% 的尺寸（门槛和区分度要求不变），Go 与安卓 C++ 同步。视频 103 帧：左侧名字 96 → 103 帧；模拟 20:9 手机 1280×576 采集：55 → 102 帧、4 颗豆都读出 49 → 92 帧，左侧替身时间线（f00180 用掉、f00525 回来、f01080 用掉、f01245 回来）与画面一致。冻结语料其余部分输出不变。

- **手机认不出名字**（视频 `火影忍者(15).mp4`，排位决斗，1920×1080，16.6 秒）：
  - **右边忍者名（神秘面具男）**：手机没有文字识别，普通忍者只能靠头像。图鉴里有这张头像（90174），但 70px 老图标在 HUD 里约按 0.72 倍显示，头像全量扫描只按 0.60 倍和一个过大的粗定位框找，排不进候选。现在扫描认不出时按头像本身再找一次（两代图标各自的显示倍率），扫描已认出的结果不变。视频 67 帧右侧名字 0 → 62 帧（1920/1600/1280 宽一样）；一致性语料另外多认出 4 个忍者（佩恩·天道[超]、药师兜[半蛇斗篷]、神秘面具男、大筒木浦式[异星钓者]，都对），视频 13 多认出一帧，其余不变；Go 与 C++ 一致。
  - **我方/对面（一直“待认边”）**：手机认边只靠账号名**图片**——「我的名字」加上同名的账号名截图，且导入的图片只在**对战加载（VS）画面**底部比对；对局中血条上方的账号名手机认不出（没有文字识别，也没有导入这种图的入口；决斗时引擎认“对局”靠的顶部回合标志又被我们的卡片盖住，认边根本不会去读顶部）。这段视频从对局开始，左边自己的「白方小…」被支援忍者头像挡住一半，右边「爱有天意…」后面带装饰符号，所以这段画面里手机无论如何认不出边。电脑版不同：悬浮窗不在采集画面里，顶部回合标志可见，对局中会读顶部账号（OCR 或 `assets/identity/fight` 模板）；但这段画面 OCR 也难：左边账号被挡、缺右括号，右边的装饰符号若被读成非字母字符，账号会被拒。需要用户：「我的名字」填 `白方小`，在对战加载画面截屏、裁下底部自己的账号名导入（标签同名）；或者直接选左边/右边。界面改了：主界面“待认边”后写出原因；账号名图片一节写清楚怎么截、怎么裁；导入时按本机屏幕换算到识别尺寸（以前 1440p/720p 的手机导入的图大小不对，永远认不出）。
  - 另：按录像帧在主机上复查，引擎一直没确认“对局”（决斗的顶部回合标志被卡片盖住，只剩续场用的替身按钮模板；手机卡片上的“对局”是录像开始前确认的）。这是单独的问题，这次没改。

## 验证

- **一致性语料**（`/ssd/work/perf-corpus`，不在仓库里）：17 张真实画面（单张 + 整段序列）+ 194 个校准、180 个能量条、16 个几何、336 个分辨率矩阵合成用例。合并后 Go 与 C++ 输出都与 v0.24beta 的参考输出 `cmp` 完全一致（两边在这套语料上也互相一致）。
- Go：`go test ./internal/...` 失败项与 v0.24beta 相同（都缺私有截图/配置），另有一个计时敏感的诊断用例现在能过。新增的点积/灰度/取帧等价测试全部通过，含 `-race`。
- C++：`hud_start_test.sh` 与之前停在同一处；新增内核等价测试约 260 万项通过；APK（arm64-v8a、x86_64）编译通过。
- AVX2 内核在 QEMU（Haswell）里验证；NEON/DotProd 在 x86 模拟和反汇编中验证。

## 待实机确认

1. Windows 真机：MuMu 截图（直接写帧缓冲）、PrintWindow 采集、AVX2 实际速度。测试工具已准备好（`timer-lab` 新旧两版对比、`match` 内核测试、Windows 版 `gocheck` 对 17 张真实画面），等电脑在线再跑。
2. 安卓真机（arm64）：NEON/DotProd 速度与正确性，60/90/120 Hz 屏幕。

## 待决定

安卓 14+ 的录屏实际是按**屏幕原生分辨率**采集（例如 2400×1080），不是文档写的 1280 宽：内容尺寸回调把录屏改成了全尺寸。改回 1280 宽是 6 行改动：模拟器上对局每帧 260–460 ms → 51–82 ms，内存再省约 10 MB（手机上帧缓冲约省 22 MB）；代价是 12 张真实画面里场景、布局、豆全部一致，但有 2 张的忍者头像结果不同（一张认不出、一张多认出一个）。未改，等确认。
