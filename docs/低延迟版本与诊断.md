# 低延迟版本与诊断

正式前端现支持按需开启阶段追踪、P50/P95/P99 报告与采集原帧录制，使用方法和指标边界见 [前端诊断与原帧录制](前端诊断与原帧录制.md)。

本轮仍只使用渲染后的屏幕像素。没有游戏进程内存读取、注入或 APK 修改。

## 启动

双击根目录 `启动计时器.bat`。`build.bat` 同时生成正式程序、调试程序、校准工具、CLI 与 `timer-lab.exe`。默认构建使用 RGB 引擎，不依赖 OpenCV DLL；原有 `-tags opencv` 是另一种显式构建。

本机配置通过 MuMu 自带 `external_renderer_ipc.dll` 截图；安装根目录、实例号和显示 ID 位于 `config.json` 的 `capture.mumu`。只调用连接、截图、显示 ID 和断开接口。截图失败会等待重连。最小化不退出，也不强行恢复模拟器；低帧率会自然降低有效观测频率。

MuMu SDK 输出安卓原始显示，PrintWindow 输出 Windows 客户区，两者可能包含不同的顶部栏。**更换截图来源时必须校验对应布局；本机采用原始显示坐标，因此不自动回退到旧窗口截图。** 兼容后端仍可供单独诊断使用。

## 行为变化

- 训练场 `camp` 与决斗场 `duel` 的坐标独立配置，场景模板明确指定对应布局。
- `layout.beadsPerSide` 默认 4；不存在的第 5/6 槽不参与观测。使用 6 槽时必须同时提供对应坐标和合法序列。
- UI 只显示本次可信的豆数；场景未知或截图失败显示左?/右?，一侧看不清仅该侧显示?。已确认冷却独立继续走秒。未知、乱序、重复图像不会凑确认帧。
- 已标定布局只采豆心，不再追逐暗豆周围的亮蓝描边；金色仍计为可用豆。冲突场景会等待，训练／决斗切换会重建计时基线。
- 灰度图每帧只转换一次，缩放后的模板按分辨率缓存。场景分数必须来自通过自身阈值的同一模板。
- 对局采样目标周期默认 16ms，周期包括处理耗时；处理慢时不会继续追加完整等待时间。
- 采集只有一个原生调用在途。超时返回等待状态，不产生无限积压的截图调用。
- `CapturedAt` 是取得图片的时间；SDK没有源画面时间戳，因此不把它声称为游戏内部事件的精确发生时间。

## 测采集耗时

在项目根目录运行，输出目录必须是新的目录：

```powershell
.\bin\timer-lab.exe capture -backend mumu -install-dir 'E:\Program Files\Netease\MuMu' -package com.tencent.KiHan -duration 10s -interval 16ms -out debug\capture-check-01
```

输出 `summary.json`、`frames.jsonl` 和第一张图。检查第一张图是否为正确游戏画面，再看错误数、采样速率和采集耗时分位数。

**采集耗时不是端到端延迟。** `changedImagesPerSecond` 表示内容变化的图片数量，不能当作游戏渲染帧率。像素没变可能是静止场景，也可能是重复图像；接口没有源时间戳，无法仅凭它区分。

## 录制与回放

保存连续 PNG（PNG 编码和磁盘写入会降低采样频率，因此录制模式不能替代前面的采集性能测试）：

```powershell
.\bin\timer-lab.exe capture -backend mumu -install-dir 'E:\Program Files\Netease\MuMu' -package com.tencent.KiHan -duration 10s -interval 33ms -record -out debug\recording-01
.\bin\timer-lab.exe replay -manifest debug\recording-01\frames.jsonl -out debug\replay-01
```

回放输出：

- `observations.jsonl`：每张图的场景、布局引擎、左右豆数（看不清为 null）、重复标记和识别耗时。
- `events.jsonl`：检测到的替身事件，包含首次观察、确认时刻和确认等待时间。
- `summary.json`：分析耗时分位数、未知观测数和事件数。

仅检查已有截图及算法耗时：

```powershell
.\bin\timer-lab.exe replay -image inbox\fight\duel_live_20260821.png -repeat 20 -out debug\single-image-check-01
```

单图重复测试不代表真实事件准确率，重复图片不参与第二次事件确认。

## 测完整识别路径

```powershell
.\bin\timer-lab.exe observe -duration 10s -out debug\pipeline-check-01
```

使用与正式程序相同的配置和截图管线，仅写每帧元数据，不编码 PNG。报告采集、分析、交付耗时，以及场景、布局、豆数、重复图片和错误。这个耗时仍不包括游戏渲染排队、事件确认等待以及浮窗显示。

## 2026-09-06 场景稳定与分辨率修复

这轮复现了三个独立问题：场景模板缩小尺寸时直接截断，800×450 下少一个像素便无法匹配；顶部回合字样暂时消失就立刻中断全部观测；结算前景与残留回合字样互相竞争，两个区域都认出结算仍可能返回未知。另外，浮窗曾把已识别的 VS、匹配、选人名称覆盖成“画面未识别”。

当前处理规则：

- 模板尺寸改为四舍五入；场景和豆坐标共用实际内容区映射。4 张训练/决斗实图的 640、800、960、1280、1600、1920、2560 宽度双线性缩放用例检查完整场景与豆数，共 28 例；纯豆数层另覆盖最近邻/双线性缩放的 56 例。
- 已确认对局后，顶部文字短暂失配时，必须同时有当前左右两侧豆区证据和攻击按钮图案，才能继续采豆计时。按钮模板不能单独建立对局。若豆区也遮挡，只保留最多 750ms 的场景名称，暂停事件确认，豆显示问号；明确 VS、选人、结算等页面立即覆盖旧对局上下文。
- 训练/决斗坐标切换需要两张不同的新画面确认，避免单帧误识别重置冷却。切换截图尺寸或采集来源时重建豆数基线，已有冷却继续运行，缩放过渡不当作替身。
- 结算等页面若在两个不重叠区域同时匹配，且最高得分不低于残留战斗文字，则确认前景页面。单区域仍保留原有竞争分差要求，未整体放宽阈值。
- 普通页已有实图覆盖大厅、匹配、选人、禁用忍者、VS、结算；9 张页面图在 8 个分辨率下回归，共 72 例。禁用页原先被“返回”按钮误归为大厅，现有独立模板和名称。未覆盖的菜单不会被猜成具体页面。

修改 MuMu 窗口大小一般不会改变 SDK 返回的 Android 渲染尺寸；修改 Android 分辨率则会重新计算映射。已验证的范围是上述 16:9 缩放，以及带真实对称黑边的画面。auto 模式不再仅凭宽高猜黑边：原生非 16:9 且没有可确认黑边时显示“画面比例未校准”，停止豆数观测，需要该比例的实图校准。显式 stretch/letterbox 配置仍按人工指定处理。

## 2026-09-06 连续替身编号与旧读秒遮挡

用户反馈旧计时尚有 0.1/0.01 秒时再次替身，界面像是漏检。代码复现表明，已确认的新掉豆不受旧冷却是否到期限制，但旧界面总是显示最早计时。例如后台已有 `[0.100, 14.968]`，界面仍显示 `0.1`；旧值为 `0.010` 时甚至显示破折号。

主读秒现显示最新一次确认事件，旧计时不会挡住它。读秒右侧增加小字“第 1 次 / 第 2 次 …”，表示当前这场该侧已确认的替身次数。编号不会随冷却结束、遮挡或分辨率重同步消失，确认进入新一局时归零；切换己方左右位置时显示对应对手的编号。尚未确认己方位置时显示左右各自次数。回放事件日志增加 `eventNumber`，诊断用全局序号仍保持单调。

编号与读秒文本独立刷新，即使新旧读秒取到 0.1 秒档后显示相同，也会更新编号。新事件到期后不会重新显示更早的旧计时。回归覆盖旧冷却剩 100ms、10ms、掉豆首帧与确认帧跨越旧到期时刻，以及相同读秒文本下的编号更新、对手换边、编号到期保留与新局重置。渲染预览在 `debug/event-number-verification-20260906/`，其中数字是排版演示。

本轮没有降低视觉阈值或减少确认帧。编号只能记录已确认事件；如果原始截图没有足够掉豆证据，编号不会凭空递增。修改前源码在 `debug/event-number-backup-20260906/`。
