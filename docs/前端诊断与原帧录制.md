# 前端诊断与原帧录制

使用 `build.bat` 构建后启动 `bin/timer-app.exe`，直接点击浮窗底部的「诊断」按钮，打开独立的诊断与录制窗口。也可以点击「设置」顶部固定的「采集与延迟诊断 / 原帧录制」入口，无需向下滚动。更新后需要关闭旧程序并重新启动。

1. 只需要阶段耗时和识别日志时，直接点击「开始诊断」。
2. 需要定位误判、漏判时，先勾选「仅在对局中录制原帧（无损 PNG）」，再开始诊断。进场自动开始保存原帧，离场自动暂停，无需重复开关；训练场识别为对局时也可录制。
3. 操作游戏复现问题；诊断窗口会显示采集次数、有效帧、绘制样本、原帧保存数、场景跳过数、丢帧与日志错误。「场景跳过」表示有图像但因不满足对局保存条件而主动跳过，不计入「丢帧」。
4. 点击「停止并生成报告」，等待后台保存完成，再点击「打开日志目录」。运行期间也可以「导出当前报告」。

开关仅针对本次运行，不写入持久配置。关闭诊断窗口不会停止会话，需要点击「停止并生成报告」结束。每次开始创建独立目录，不覆盖之前的记录。原有 `NARUTO_DEBUG=1` 或 `debug.enabled=true` 会在启动时自动开启诊断日志，但不会自动开启原帧录制。

## 输出与排障

默认输出位于 `debug/sessions/` 下的独立会话目录（根目录跟随 `config.json` 的 `debug.directory`）：

- `capture.jsonl`：采集尝试、识别结果、事件和 UI 阶段记录，通过帧编号关联。包括采集方法与源序号、尺寸、重复/未知/失败状态、场景、布局、名字、忍者、每颗豆的判定与置信度，以及异常原因。
- 原帧 PNG：仅对局中满足保存条件的当前帧，按采集源返回的原分辨率无损保存，不缩放、不叠加标注。MuMu SDK 是 Android 显示画面；PrintWindow 是窗口客户区，具体以日志的采集方法为准。不是摄像机视频或 SDK 内存字节转储。
- `hud/`：录制开关开启后，每秒最多保存两张名字与豆区域的原像素 PNG；只裁剪、不缩放。其 `hud_frame` 日志包含帧号、裁剪坐标与原图尺寸，可关联同一帧的识别结果。全帧额度用完后继续使用预留额度保存 HUD；这不是完整画面，不加入完整帧回放清单。
- `frames.jsonl`：回放清单，成功保存的帧带有图片路径；失败、无图或录制丢弃的尝试保留空路径和错误，避免回放跨过缺失画面继续确认。可以交给现有 `timer-lab replay` 重跑识别。
- `report.json`、`report.md`：各阶段 P50/P95/P99、样本数、排除原因，以及录制/日志丢失和写入错误。
- 会话元数据包含本次配置，便于对比采样周期、确认帧数、识别布局等条件。

从异常事件找到确认帧与首次观察帧，再按帧编号查看原图及相邻帧的豆数、未知状态、重复标记和场景变化。原帧复制和 PNG 保存仅在当前帧同时满足 `Fighting=true`、`Scene=fight`、`Hold=false`、`Err=nil` 时进行，不沿用上一帧的对局状态。大厅、匹配、选人、结算、未知/保持状态，以及采集或分析失败的帧不保存 PNG，只保留有数量限制的轻量元数据，供排查场景切换和停止确认的原因。截图失败没有图片时，只记录失败，绝不沿用上一张图片冒充新帧。

回放示例（目录替换为实际会话目录）：

```powershell
.\bin\timer-lab.exe replay -manifest 'debug\sessions\实际会话\frames.jsonl' -out 'debug\本次回放'
```

录制清单只引用成功落盘的图片。出现录制丢帧时不能把回放视为原始连续采集的完整复现；先检查日志与报告中的缺失。采集、事件与 UI 日志使用独立队列，PNG 编码不会阻塞日志写入。图片队列满时保留采集元数据；回放遇到帧编号缺口会重建观测基线，不能跨丢失帧继续确认事件。后台 OCR 的诊断记录表示此帧消费到的结果，不表示 OCR 一定由同一帧同步产生。

`player_side` 是该帧新提供的身份观察值；身份识别有采样间隔，空值不代表前端已经丢失所记忆的己方位置。不同后台写入的记录以 `frame_id` 关联，不依赖在 JSONL 中相邻或出现顺序。

## 时间边界

所有链路使用同一进程的时间戳，计算时保留 Go 单调时钟：

| 阶段 | 边界与含义 |
|---|---|
| 采集 | 原生采集请求开始 → 成功取得图像 |
| 分析 | 真正进入识别引擎 → 分析完成；校验跳过不产生分析样本 |
| 交付 | 分析完成 → 正式 UI 采集工作线程拿到结果 |
| 事件确认 | 首次掉豆图像取得 → `SideClock` 确认事件；包含多帧证据等待 |
| UI 投递/应用 | 准备投递 → Fyne 主线程完成对应帧的标签与计时更新 |
| 绘制等待 | UI 更新完成 → 原生窗口开始绘制 |
| 绘制/提交 | 原生窗口绘制开始 → `SwapBuffers` 返回 |
| 帧应用内端到端 | 该帧采集请求开始 → 对应 UI 内容完成原生缓冲提交 |
| 事件应用内端到端 | 首次掉豆证据帧的采集请求开始 → 确认帧对应提示完成原生缓冲提交 |

采集源没有游戏内部渲染时间戳；`SwapBuffers` 返回也不能证明显示器已经扫描出画面。因此报告不宣称测到了「游戏事件发生到人眼看到提示」的物理延迟。

**只有完整、可信、时序合法且真正绘制的链路才进入应用内端到端分位数。** 无图像、失败、未完成分析、未知/保持状态、重复图像、被新 UI 更新覆盖、缺失绘制回调或时间戳不全的样本不会被填成 0ms。没有合格样本时指标是不可用/null，并保留对应计数。未显示在浮窗上的另一侧事件不会冒充已显示事件；诊断开始前的首次证据无法补造。重复重绘同一帧也不增加样本数。

已有 CLI `observe` 和离线 `replay` 没有浮窗绘制链路，只报告流水线或分析耗时；其调用耗时不能作为端到端延迟。

## 负载与构建

PNG 编码和写入在有界后台队列执行，采集线程仅对符合条件的当前对局帧复制像素；非对局帧不进入像素队列。前端录制的总上限仍为 1 GiB，其中 768 MiB 用于完整原帧，256 MiB 专用于每秒最多两张的 HUD 证据，避免整场的额度全被开头的全帧占用。HUD 也有上限，并不保证无限时长保存。像素队列总计最多 64 MiB，预留八分之一用于轻量证据；日志与图片分别由后台队列写入，日志总量与追踪历史也有限制。达到限制时会记录丢失或排除，不无限占用内存或磁盘。原帧复制、日志和诊断重绘本身都有开销，录制时的分位数包含这些运行条件，不能混同关闭录制的性能基准。

Fyne 2.6.3 没有公开的原生绘制结束回调。`scripts/fyne-diagnostics/prepare.ps1` 根据本机已安装的固定版本生成一个小型 Go 构建 overlay，由 `build.bat` 应用：在真正绘制之前及可见窗口的缓冲提交之后打点。它校验版本与补丁位置，不修改 Go 模块缓存或依赖源码。产物只在 `bin/fyne-diagnostics/` 中；升级 Fyne 时需要重新审查补丁。

直接运行普通 `go build` 仍可编译运行，但不会注入此回调；界面会显示「端到端指标不可用」，报告只保留已经测到的阶段。`Refresh` 返回、`fyne.Do` 返回、软件渲染预览均不会被当作原生绘制完成。
