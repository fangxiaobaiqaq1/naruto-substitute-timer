# 发布签名清单设计（UR-01，未实现）

状态：设计草案，**没有接入代码和 workflow**。是否采用、密钥由谁保管，需要维护者决定。

## 要解决的问题

现在在线更新只认两样东西：TLS 和发布托管账号。

- GitHub 源的 SHA-256 来自 API 的 `digest`，它是 GitHub 根据上传的字节算出来的。
- Gitee 源（默认源）的 SHA-256 来自同一个 release 里的 `SHA256SUMS.txt`。

所以谁能写 release，谁就能给所有客户端推送代码：维护者账号、泄露的 `GITEE_TOKEN`、被攻破的 CI 或托管平台都可以。Android 端有 APK 签名兜底；Windows 端没有任何发布者签名。

## 方案：离线 Ed25519 签名的发布清单

每个版本多发布两个附件，GitHub 和 Gitee 上内容相同：

- `release-manifest.json`：
  `{"schema":1,"tag":"v0.3.0","files":{"timer-app.exe":{"sha256":"…","size":…},"naruto-timer-universal.apk":{"sha256":"…","size":…}}}`
- `release-manifest.json.sig`：对清单原始字节的 Ed25519 签名（64 字节，base64）。

Go 端直接用标准库 `crypto/ed25519`，不需要新依赖；Android 端用 BouncyCastle 或 API 33+ 的 Ed25519。

### 密钥放在哪里

- 私钥**不进 CI、不进仓库**。放在维护者自己的机器上，用口令加密保存（例如 `age` 加密的 32 字节种子），或者放在支持 Ed25519 的硬件密钥里。另做一份离线备份（纸质或加密 U 盘）。
- 公钥以常量形式编译进 `internal/updates` 和 APK。预留两个槽位：当前密钥和下一把密钥。轮换时，先发一个同时信任新旧两把公钥的版本，再改用新钥签名。

### 签名流程

1. 推送 tag 后，CI 照常构建，并额外生成**未签名的** `release-manifest.json`，以 artifact 形式上传，不直接发布。
2. 维护者在本地运行一个小工具（将来的 `go run ./cmd/sign-release`，现在还没有）：
   - 下载 CI artifact，独立重算每个文件的 SHA-256 和大小；
   - 与清单比对，确认 tag 和提交一致；
   - 用离线私钥签名，然后把清单和签名上传到 GitHub 与 Gitee 两个 release。
3. 备选方案：CI 签名，但私钥只放在受保护 Environment 的 secret 里，并要求维护者审批。这比现状好，但仍然信任 GitHub，并且密钥在线。

### 客户端校验（Windows `internal/updates`，Android `UpdateManager`）

1. 用现有的严格跳转策略下载清单和签名，各自限制在 64 KiB 以内。
2. 用内置公钥验签，并要求 `manifest.tag` 等于所选 release 的 tag。
3. 下载的 EXE/APK 的 SHA-256 和大小**只取自清单**。API 的 `digest` 和 `SHA256SUMS.txt` 降级为可选的交叉校验。
4. Android 端继续校验 APK 的包名、`versionCode` 和签名证书（UR-04）。

### 上线步骤

- 版本 N：客户端带上验签逻辑，但缺少清单时只记日志，不阻止更新；从这个版本起每次发布都附带清单和签名。
- 版本 N+1：没有有效签名就拒绝更新，界面提示“请从发布页手动下载”。
- 另外建议：开启 GitHub 的 immutable releases，为 `v*` 标签设置保护规则；可选给 `timer-app.exe` 做 Authenticode 签名，并在 `apply()` 里用 WinVerifyTrust 检查发布者。

## 这个方案不能解决的问题

- 私钥本身泄露。缓解办法：离线保存，轮换槽位。
- 镜像源扣住新版本不发（冻结更新）。清单可以加上过期时间来缓解，但离线签名就得定期重新签。
- 首次安装包本身的真实性。仍然依赖下载渠道，以及将来可能加上的 Authenticode 签名。
