# 豆变化 → 起钟链路修复验证

## 对上次测试结论的更正

上次的 12 张图 / 48 个用例验证的是静态豆数、布局和场景结果，没有经过连续采集、事件确认和计时显示。它不能证明实战中会起钟。原测试结果仍然成立，但不能当作端到端验收。

本次用户提供的 1024×461 截图保留在本地 `inbox/regressions/wide-overlay-beans-20261009.png`，不随源码或测试包分发。

## 实际复现的两个阻断点

### 1. 豆数已经读到，但场景门闩不放行

修复前，两端识别结果一致：

```text
fight=0 unc=1 gate=0.3140 profile=duel
左 1 / 右 4，8 颗豆状态均可知
```

顶部浮窗遮住回合标记；宽屏下两个备用战斗控件也落到了旧搜索区之外。native 将结果标记 Hold，Session 提前返回，因此这些豆数不会送入 SideClock。

修正：扩大对应的两个控件搜索区域，不降低模板阈值。首次进入对局的备用路径要求 **两个独立区域的战斗控件通过原阈值 + 两侧完整合法、高置信的当前豆排**；明确的其他页面、竞争布局、缺失槽和单个控件都不能绕过门闩，也不凭首次读到的豆数开钟。

修复后，同一张未改动截图：

```text
fight=1 unc=0 scene=fight gate=0.8669 profile=duel
左 1 / 右 4，8 颗豆状态均可知
```

### 2. 重复采集被误当成采集中断

真实 JNI 链复现：16ms 间隔建立基线后，持续重新采集相同像素约 1 秒；随后两个独立帧都读到单豆下降，旧代码仍是“第 0 次”，没有倒计时。

修正：新采集到的重复像素只维持已有基线 / 待确认观测的有效时间，**不增加确认票、不修改事件时刻、不跨越已超时的采集间隙**。Windows 和 Android 同步。没有新采集的 heartbeat 仍是无操作，乱序时间和不完整豆排不能维持观察。

Android 无钟文案同时区分“待采集 / 待识别 / 待机 / 待认边 / 待替身”，不再把所有无倒计时情况显示为“待机”；已确认的时钟在遮挡或采集错误期间继续按原时间运行。

## 本次真正跑过的链路

### Windows 逻辑

```text
完整像素帧 → factory → frame.AnalyzeImage → UI captureOnce → SideClock
```

`internal/ui/overlay_observation_test.go` 用用户截图构造明确标注的受控 **2→1→1** 像素序列，未手填 Fighting、Hold 或豆数跳过识别。首帧只建基线，第二帧记录降豆时刻，第三帧确认：事件数 1，剩余 14.9 秒。

### Android 逻辑

```text
PNG / 受控像素修改 → 生产 C++ Pipeline → 生产 jni.cpp
→ 真实 NativeCore.Decoder → 真实 Settings / Session / SideClock → OverlayState
```

入口：`android/tools/chaincheck/run.sh`。只为主机缺少的 Android 平台壳提供 stub；没有复制计时算法、另造解码器或注入 Fighting/Hold 标志。

已通过的 8 组受控场景：

| 场景 | 实际断言 |
|---|---|
| 无钟状态区分 | 等待采集、证据不足、未认边、待替身等文案正确 |
| 100ms 间隔 2→1→1 | `第 1 次`，`14.9`；时刻取第一张降豆帧 |
| 重复帧 / heartbeat | 不凑确认票；新独立帧才能确认 |
| 控件遮挡打断确认 | 即使豆数完整，也不能沿用遮挡前的待确认票 |
| 我方在右，只右侧掉豆 | 右侧诊断钟启动；左侧对手主钟和事件数不变 |
| 333ms 采集间隔 | 正常确认，扣除等待时间后显示 `14.6` |
| 连续重复采集约 1 秒后掉豆 | 不再吞掉事件；`第 1 次`、`14.9` |
| 只有 heartbeat、没有采集 | 不连接采集黑洞两端的豆数，不猜测起钟 |

共 2986 个断言通过，其中包括各帧的 JNI 字段、实际像素豆数、去重标志和状态输出；这是上述场景中的重复检查，**不是 2986 段实战录像**。

另已通过：Go app/engine/frame/detect/config 测试，UI/scene 定向回归，C++ 门闩正反例，原 12 张分辨率静态回归，以及 13 张图的 Go/native 输出一致性检查。

### 两端同步的算法改动

1. 仍按 `min(W/refW, H/refH)` 缩放 HUD，生命条斜边按当前画面校正左右位置；允许真实红血条被紫光染色，但拒绝蓝色特效、平直色带和不合法斜率。
2. 六槽根据已标定前四槽的平均 `(dx,dy)` 延伸，保留整排偏移，不使用旧固定步长。侠隐、水门等额外能量条的行偏移仍须当前确切身份授权。
3. 侠隐红豆必须有与两侧间隙分离的实体，薄红条不能提供票；未确认身份不能把未知豆排搬到下方找亮点。
4. 公共训练控件补充“复位”和“退出”，不按忍者收集普攻按钮。控件的 **screen 搜索区域** 与 **等比模板尺寸** 分开处理；已有小 / 中 / 标准按键尺度及候选位置附近的 ±2 像素尺寸细化用于适应按键大小。接受阈值未降低。
5. 冷进入仍须两个独立的实际命中区域和完整合法的双侧豆排；相同位置的尺寸变体不重复计票，其他页面或竞争布局仍否决进入。已有普通忍者观测 / 重复采集修复保留。
